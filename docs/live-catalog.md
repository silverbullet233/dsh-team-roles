# Read-only native model catalog

Run `node scripts/live/catalog.mjs` after binding this checkout's dependencies to the complete official DSH source build at `22ddee3792402c3e70ec5f86a63c3e3e895a2f60`. The command mounts only native credentials, authorization, account and LLM services in one disposable Context. It does not load SessionController, AgentLoop, Web, BrowserAuth or a network listener, and never calls an inference API.

The default existing credential path is `/Users/mxr/.dsh/.credentials.yaml`; `DSH_NATIVE_CREDENTIALS_PATH` can name another explicitly authorized canonical native document. `ReadOnlyNativeCredentials` rejects creation, migration, replacement, refresh and deletion. The standalone script does not read `.env` files; its native launch-environment snapshot retains only an already-inherited `OPENCODE_API_KEY`, so ambient provider endpoint overrides are not inherited. No credential is persisted, exported or migrated. In an existing native host, the reusable mount function reads that host's existing native launch snapshot without changing it.

`mountNativeProviders(ctx, {credentialsPath})` is reusable by the isolated shared native Web composition. It preserves already-mounted services and native provider registrations. Otherwise it mounts the official DeepSeek account platform and adapter with `reasoningEffort: max`, and the native pi-ai adapter with the existing `opencode-go: {}` registration. It supplies no provider endpoint or credential value. The native account service resolves its existing grant only for its approved inference origin. Native pi-ai authentication resolves its route record, then uses the existing native auth context for `OPENCODE_API_KEY`: stored credential reference first, then the host's native launch snapshot. The readonly credential provider does not need its own environment fallback.

The account route performs its normal authenticated model-directory GET. OpenCode Go uses its installed pi-ai catalog and resolves its existing native route record or `OPENCODE_API_KEY` reference through native authentication. Output includes only source SHA, credential-presence booleans, provider/model names, availability and native reasoning-effort metadata. Endpoint-containing native account listing diagnostics are replaced with `accountListing`: `loaded` means a fresh native account directory response succeeded, `fallback` means native discovery used its bundled catalog after a directory failure, and `unobserved` means no successful/failing directory load was observed. `accountListingFailure` contains only a reduced transport, timeout, HTTP-status or generic failure category. Fallback is not live directory verification. `readyForRequestedLiveInference` also requires both native credential registrations and the requested `max` effort. Exit status 2 means one of those prerequisites was not established; no provider/model substitution occurs.

The two inspected routes are exactly `deepseek-account/deepseek-flash` and `opencode-go/deepseek-v4.1-flash`. Their runtime and adapter identities remain distinct from the native Team spawn backend. Catalog success establishes supported routing metadata only; it does not establish successful inference, collaboration, recovery or rendered native Web behavior.

## Standalone metadata on 2026-10-25

The metadata GET succeeded through the native DeepSeek account adapter after a sandboxed transport failure was retried with narrow network access. `deepseek-account/deepseek-flash` was offered as `DeepSeek-V4.1-Flash`, with `off`, `low`, `high` and `max`; its adapter default was `max`. The native installed OpenCode Go catalog offered `opencode-go/deepseek-v4.1-flash` as `DeepSeek V4.1 Flash`, with `low`, `high` and `max`, and no selected default effort.

That standalone command found the native DeepSeek account grant, but no `llm-pi-ai/opencode-go` record or stored `OPENCODE_API_KEY` reference. Its own inherited process lacked `OPENCODE_API_KEY`, and `/Users/mxr/.dsh/.env` was absent. Its readiness result was therefore false for that launch environment. The command did not inspect another process's environment or extract browser credentials; no inference, credential write, refresh, copy, migration or host listener occurred during that catalog check.

## Installed native host and live verification

The user-authorized native host was subsequently launched through its ordinary `zsh -ic` environment, which already supplied the existing OpenCode reference from the user's shell configuration. The host's native launch snapshot reported OpenCode authentication present. This environment differs from the earlier standalone command; no key was extracted, copied or persisted by the plugin.

Actual member `calc-left` used `opencode-go/deepseek-v4.1-flash` with `max` alongside `calc-right` using `deepseek-account/deepseek-flash` with `max` in the same native Team. Audited payloads, native request headers, fixture read/write results and peer messages verified both routes. A later outer Codex continuation reused the existing OpenCode member. See [live results](validation.md).

The final live audit contained 23 payloads within a 24-payload budget, including one blocked preflight and 22 permitted adapter submissions; HTTP retry counts were not measured. Live inference permission was removed after validation. The catalog command remains read-only discovery, and its readiness always describes the particular native launch environment being inspected.
