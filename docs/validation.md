# Portable package validation

The current plugin version is 0.3.0. Local tarball installation is tested; npm/GitHub publication and registry name ownership are not. The test uses the exact supported official source build and the native installation/profile resolver. It does not modify the active user's profile or restart their Web host.

## Actual isolated installation and loading

The built tarball was installed with native `dsh plugin --profile role-package add <absolute-local-tarball> --ignore-scripts` into a newly initialized temporary Harness home. Ordinary npm libraries installed normally; the profile contains no manual links to the development plugin checkout and no separately installed native DSH service copies. The plugin itself is a normal directory, not a link to source. The runtime was moved to a second directory and its path-specific package-store metadata changed; a fresh second profile repeated installation and keyless loading.

A copy-on-write relocated fixture contains tracked official DSH source at `22ddee3792402c3e70ec5f86a63c3e3e895a2f60`, complete build artifacts, dependencies and the official native addon. Root environment files and user account/credential/session data were excluded. Official `PluginPackages` runtime resolution and app boot loaded the installed package with the relocated CLI installation anchor. Every verified native import and serving service identity belonged to that relocated runtime.

Fresh installation loaded an empty catalog without a legacy JSON file. A private IPC create request succeeded with the native main Agent selection. After changing its actual native provider/model/effort, a native teammate inherited that exact request route; no plugin fallback route was synthesized. Saving a synthetic native role catalog succeeded through actual Settings/ConfigEditor; stale edits and unavailable models were rejected, with invalid input leaving the profile bytes unchanged. A private IPC create and native teammate spawn then completed with scripted keyless adapters. The test observed the native roster and exact child route, then cleared the catalog while preserving an existing managed Lead reservation. No paid provider was called.

Negative controls removed `AgentModel.prototype.select` only inside the isolated test process: plugin activation returned `DSH_RUNTIME_INCOMPATIBLE`, opened no IPC socket and submitted zero model requests. Loading the tarball with plain Node outside the official native resolver returned actionable `DSH_NATIVE_PEERS_UNAVAILABLE`. No source/runtime fallback was selected.

## Test scope

Repository unit/native tests retain coverage for immutable snapshots, changed/removed-role recovery, same-member follow-up, projection/selection durability, IPC idempotency, approvals and HMR-safe Settings transactions. Package regressions reject source-only archives, wrong client assets and machine-specific release paths. Build/pack checks include the generated native client and portable verification seal, with no native service bundles or local dependency links.

This is keyless integration evidence, not new real-provider inference. Prior live dual-provider/Codex/browser evidence remains in earlier Git checkpoints; it is not replayed by portability tests. Usage and fees remain unknown; inputs are text-only. Another operating system/architecture and a different physical machine have not been independently exercised. The complete suites passed 52 unit, 25 native integration and 5 runtime tests. To reproduce package acceptance, run `node scripts/test-portable-package.mjs <compatible-runtime> <built-tarball>`; it initializes an isolated temporary profile, installs through the native CLI, and runs positive, missing-API and outside-launcher controls. Logs and route evidence remain in its printed temporary home. The Settings/browser assets were rebuilt; this portability run exercises the real Settings service and does not claim a new browser interaction on the user's active Web.
